# Deploying Hermes Workspace (self-healing build)

This fork of `hermes-workspace` is designed to run **on top of a vanilla
Hermes Agent install with no workspace-side patches to Hermes Agent itself**.
All fixes for the "Skills unavailable / gateway race" class of errors live
**inside this repo** — there is nothing to tweak in Hermes Agent.

## Architecture (what must be running)

```
hermes-agent gateway   → :8642   (hermes gateway run)
hermes-agent dashboard → :9119   (hermes dashboard)
hermes-workspace       → :3001   (this repo, reverse-proxied via caddy/nginx)
```

Workspace is a thin frontend + light backend. It needs the Hermes gateway
for chat/model/MCP and the dashboard for Sessions/Skills/Config/Jobs. Without
Hermes Agent it will not function — but you install Hermes Agent **normally**
(no modifications) and this workspace connects to it.

## Install Hermes Agent (vanilla, no edits)

```bash
# follow upstream Nous Research instructions, e.g.
git clone https://github.com/NousResearch/hermes-agent
cd hermes-agent && pip install -e .
# start services (systemd units or `hermes gateway run` / `hermes dashboard`)
```

Ensure the gateway is reachable on `127.0.0.1:8642` and the dashboard on
`127.0.0.1:9119`. The dashboard will prompt for auth (Public Bind) — create a
login as usual.

## Install this workspace

```bash
git clone <your-fork> hermes-workspace
cd hermes-workspace
npm install
export NODE_OPTIONS="--max-old-space-size=1536"   # smaller boxen
npm run build
```

## Configure secrets (out of repo)

Create `/root/.hermes/workspace_env.conf` (chmod 600). It must contain the
values workspace uses to talk to the gateway + dashboard:

```
HERMES_API_TOKEN=<token from hermes agent config / API server key>
HERMES_PASSWORD=<workspace login password>
HERMES_WORKSPACE_DIR=/root/workspace

# Dashboard basic-auth credentials — MUST match what the dashboard on :9119
# actually expects. Get them from the running dashboard's environment:
#   tr '\0' '\n' < /proc/$(pgrep -f 'hermes dashboard')/environ \
#     | grep HERMES_DASHBOARD_BASIC_AUTH
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=<the dashboard's password>
```

> The dashboard password is generated by Hermes Agent at install time. Copy
> the real one from the running dashboard process (shown above) — do NOT
> invent one. If it mismatches, the workspace logs
> `Dashboard login rejected` and Skills stays unavailable.

## Systemd unit

Copy the provided unit (it already contains the readiness wait + self-heal
hooks this build relies on):

```bash
cp deploy/hermes-workspace.service /etc/systemd/system/hermes-workspace.service
systemctl daemon-reload
systemctl enable --now hermes-workspace
```

The unit sets `HERMES_API_URL`/`:8642` and `HERMES_DASHBOARD_URL`/`:9119`
directly. There is **no `:9120` loopback proxy** — it is not needed.

## How self-healing works (no Hermes Agent edits required)

`src/server/gateway-capabilities.ts`:

1. `probeDashboard()` retries `/api/status` with backoff and falls back to the
   authenticated fetch path, so a dashboard that is still booting (or auth-
   gated) does not latch a permanent `available=false`.
2. `startGatewayWatchdog()` (auto-started on first capability check) re-probes
   every 20s and upgrades the mode to `zero-fork` the moment the gateway /
   dashboard become reachable — even if workspace booted before them. It stops
   itself once fully connected. This removes the "Skills unavailable until I
   restart workspace" race entirely.

Result: install Hermes Agent normally, point workspace at `:8642`/`:9119`, and
the workspace recovers on its own. No manual fixes inside Hermes Agent.
